# MQTT driver, JSON and plain payloads. Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax. Tick each step when it is done, in the same work block.

**Goal:** a read-only `mqtt` input that subscribes to a broker over MQTT 3.1.1 (TCP or TLS, optional authentication), turns JSON and plain payloads into typed samples through `topic|path` addresses, keeps its devices alive while the broker is connected, kills and revives them through optional availability topics, and offers `probe` and `browse`, tested against a broker started inside the tests.

**Architecture:** the driver `internal/input/mqtt`: connection and address parsing, a pure message decoder (payload to samples), an availability tracker on top of the core's `input.Lifecycle`, a small client interface with an adapter over paho, and the input itself (one goroutine owning the connection, its own reconnect loop with the driver kit's backoff, the subscription set persisted per input). It registers in the `run` driver registry, becomes accepted by `CheckBuild`, and plugs into `probe` and `browse`.

**Tech Stack:** Go 1.27; new dependency `github.com/eclipse/paho.mqtt.golang` v1.5.1 (`EPL-2.0 or BSD-3-Clause`, taken under BSD-3-Clause; brings `github.com/gorilla/websocket`, `golang.org/x/net`, `golang.org/x/sync`); test-only dependency `github.com/mochi-mqtt/server/v2` v2.7.9 (MIT). Both approved by the user on 2026-11-06.

**Spec:** `../specs/2026-11-06-mqtt-driver-design.md` sections 2 to 6 and 8 (plan 1); parent `../../../../docs/superpowers/specs/2026-10-12-laraplate-edge-agent-design.md` 9.1, 9.2; `../specs/2026-10-19-transforms-modbus-opcua-design.md` D6 and section 7 (driver kit, `probe`).

## Global Constraints

- AGPL-3.0 repo; permissive dependencies only; no CGO; module `github.com/getlaraplate/laraedge`; work on a feature branch from `develop`, merged through a pull request into `develop`.
- `gofmt -l .` empty, `go vet ./...`, `go test -race ./...`, `GOARCH=386 go test ./...`, `GOOS=windows go vet ./...` before every commit; table-driven tests; fakes over mocks; fake clock for scheduling, no sleeps or timing assertions (`clock.Fake.BlockUntil` to wait for timers).
- The driver never publishes: no `Publish` call anywhere in `internal/input/mqtt` in this plan (Sparkplug rebirth is plan 2).
- Input contract (core R47, spec D6): `Start` reads only local files (TLS) and returns; the broker connection runs in the background; an unreachable broker is death after `death_tolerance`, never a failing `Start`.
- Payload values, passwords and connection settings never appear in errors or logs at info and above; paho's package loggers stay at their silent defaults.
- Spec values exactly: `broker` schemes `mqtt` (port 1883) and `mqtts` (port 8883); `client_id` default `laraplate-edge-<agent_id>-<input_id>`; `qos` 0 or 1, default 1; `persistent_session` default `true`; `keepalive` default `30s`; `max_payload` default 256 KiB; `format` `json` (default) and `sparkplug_b`; timestamp formats `rfc3339`, `unix_s`, `unix_ms`; address `<topic>[|<path>]`, split at the first `|`; `+` and `#` refused in a point topic; plain `bool` accepts `true`/`false`, `1`/`0`, `on`/`off`, case-insensitive; command client ids `<client_id>-probe` and `<client_id>-browse`, clean session, QoS 0; read error kinds `payload_too_large`, `malformed_json`, `bad_timestamp`, `conversion`, `availability`, `unmapped`, plus the kit's `connection`.
- Commit only your own files in laraedge; never push; no `Co-Authored-By` trailer; do not commit at the stack root.

## Decisions taken in this plan

- **Q1. Driver configuration is validated by the factory**, as modbus M1: the schema keeps `connection` open (core R6), so the spec's "JSON Schema of the connection" is this factory validation, shown offline by `config validate` through the registry. Fixed messages naming the field path, never a value.
- **Q2. Devices are alive while the broker is connected.** `input.Lifecycle` kills a device after `death_tolerance` without `Read`. While connected, the input calls `Read` for every device that is not held dead by its availability topic, on connection and then every `death_tolerance / 2`. So silence never kills, a broker outage beyond the tolerance kills every device, and the reconnection gives the birth at once (the spec, which said "at its first sample after the connection", was amended with this plan).
- **Q3. Death on demand.** `input.Lifecycle` gains `Die(device string)`: emits death now for a live, known device, no-op otherwise. The `offline` availability payload calls it; `online` or a sample of that device calls `Read`.
- **Q4. Integers stay exact.** JSON is decoded with `json.Decoder.UseNumber`; a number goes to an integer type only when it parses as an integer in the type's range (`3.0` and `1e3` are not integers: `bad`); `uint64` above 2^63-1 is `bad` (model integers are int64, as modbus); `float32`/`float64` take the float value, non-finite is `bad`.
- **Q5. `max_payload`** is an integer number of bytes or a string with suffix `KiB` or `MiB` (`"256KiB"`), from 1 byte to 16 MiB; the check happens before any parsing.
- **Q6. Read error kinds** of this driver are exposed from their first count (the status endpoint already adds kinds outside `input.ReadErrorKinds`); `input.ReadErrorKinds` is not extended, so other drivers do not gain mqtt series.
- **Q7. The subscription set** of an input is `data_dir/mqtt/topics/{input_id}.json` (a sorted JSON list of topics), written with `atomicfile.Write` after the subscriptions of a connection are acknowledged. At connection the input unsubscribes the topics of that file it no longer uses, then subscribes its own. *Amended 2026-11-06 by the final review (R14):* the set was first kept in `data_dir/inputs/{input_id}/mqtt-topics.json`, the transform state directory, which the supervisor deletes on a rollback and when an input leaves the document; a rollback then left the failed document's topics subscribed with no record of them, so the set moved outside it.
- **Q8. `format: sparkplug_b`** and `rebirth` are refused by this build with `connection.format: not available in this build` (plan 2).
- **Q9. `probe` waits** for the first sample of every point until all points have one or the command's 30 s timeout ends; points without a message are printed as `no message`. `Probe` returns the samples it has when ctx ends, without an error.
- **Q10. Test broker.** mochi in process, plain TCP and a TLS listener with a certificate generated by the test, the auth hook for user and password; one helper in `internal/input/mqtt/mqtttest` (test files and a test-only package).

## Review Focus

- The agent is stopped while a device publishes with QoS 1; after restart with the same persistent session the messages published meanwhile arrive as samples, in order. Test in Task 5.
- A JSON integer field that overflows the point type (`70000` into `int16`), a float into an integer type (`3.5`, `3.0`), `1e400`, and a 20-digit integer: each is a `bad` sample with kind `conversion`, never a panic or a rounded value. Test in Task 2.
- A retained `offline` Last Will on the availability topic when the input starts: the device gets death right after the supervisor's birth, and no keep-alive `Read` revives it until `online` or a sample arrives. Test in Task 5.
- A reload that removes a topic: the topic is unsubscribed at the next connection; a message of it still queued in the session is dropped with kind `unmapped`, never emitted. Test in Task 5.
- `probe` and `browse` run while the agent's input is connected: the agent stays connected (different client ids). Test in Task 6.

## Delivery status (2026-11-06): shipped

All seven tasks are built on branch `feat/mqtt-json`, each reviewed. The agent has a read-only `mqtt` input
(MQTT 3.1.1 over TCP or TLS, paho under BSD-3-Clause): the factory validates the connection, the `topic|path`
addresses, the points and the availability entries offline (`config validate`, Q1), `CheckBuild` accepts `mqtt`,
`Start` reads only the TLS files and returns, and one owner goroutine connects in the background with the
driver kit's backoff, a new paho client per attempt (R8), subscriptions made again at every connection and the
subscription set kept in `data_dir/mqtt/topics/{id}.json` (Q7, amended by R14). Payloads convert losslessly to the point's
type (JSON numbers through `UseNumber`, Q4), with `bad` samples and the read error kinds `payload_too_large`,
`malformed_json`, `bad_timestamp`, `conversion`, `availability` and `unmapped` (Q6). Devices are alive while the
broker is connected, renewed every half `death_tolerance` (Q2), die when the broker is missing beyond it, and
follow an optional availability topic through the core's new `Lifecycle.Die` (Q3). `probe` and `browse` connect
as `<client_id>-probe` and `<client_id>-browse` with a clean session and QoS 0 (Q9), so they run beside the
agent. Tests run against the in-process mochi broker behind a connection-dropping front listener
(`internal/input/mqtt/mqtttest`, test-only, R1 and R7); the end-to-end test runs the built binary over TLS
through births, a live message, a payload that is not JSON, a broker stop and restart (death after the tolerance,
birth and data again) and an availability `offline` and `online`, with envelopes valid against the backend
schema. The mochi library is not in the shipped binary (`go list -deps ./cmd/... | grep mochi` is empty).
Commits from `ca40a3f` to `8e1d2a9`, `d2c428e`, the closing commit `75735f3`, its fix `96f2602`, and the
fixes of the final review (R12 to R15) from `4b2860a` on. Dependencies: `github.com/eclipse/paho.mqtt.golang`
v1.5.1 (`EPL-2.0 or BSD-3-Clause`, taken under BSD-3-Clause; brings `gorilla/websocket`, `golang.org/x/net`,
`golang.org/x/sync`) and, test-only, `github.com/mochi-mqtt/server/v2` v2.7.9 (MIT), both approved by the user on
2026-11-06. The divergences from the plan and the spec, each with its reason (the rulings are in "Controller
rulings" below):

- **Q2 amended the spec.** The spec said a device is born "at its first sample after the connection"; the
  core's `input.Lifecycle` kills a device after `death_tolerance` without a `Read`, which would make silence
  kill a device that publishes on change only, so the input renews every live device on connection and every
  half tolerance and the birth comes at the connection. The spec text was
  amended with this plan. Fix round 1 of Task 5 added one more renewal when a connection is lost, so an outage
  shorter than the tolerance does not kill a device the last renewal of which was old.
- **R9: `probe` has no arrival time per point.** The spec asked for value, type, quality and arrival time. The
  command keeps the shared output of every driver, one line per sample and one response time for the whole read,
  and prints `no message` for a point without a sample. A column can be added later.
- **R10: `browse` lists at most 100 JSON leaves per topic**, a memory bound the spec does not state, besides
  the 1000-topic cap. Dropped leaves and a payload above `max_payload` are not marked in the output.
- **R3: `timestamp` needs both `path` and `format`**, with no default format, stricter than the spec's table.
  **R5:** an unreadable timestamp marks every point of the topic `bad`, plain ones included, so a `timestamp`
  belongs on JSON topics (per topic through `topics`).
- **Read error series (Q6, precisely).** As for every input that reports its health, an `mqtt` input exposes
  `timeout`, `connection`, `exception` and `decode` at 0 from the start; this driver counts only `connection`. Its
  own kinds appear at their first count.
- **R11: `tls` file paths are read as given**, relative to the process working directory, not the document's
  directory; the documentation says to use absolute paths.
- **The `connection` kind counts a refused subscription.** A broker that refuses the subscriptions (an ACL) is
  retried at every connection and shows only as `connection` errors and deaths; the cause is logged at `debug`.
- **`probe` of an `mqtt` input reads `agent_id` from the bootstrap** (default client id), as `opcua` does.
- **Final review fixes (R12 to R15).** A payload timestamp before 1970, after year 9999 or the zero time is
  `bad_timestamp` (R12, opcua's plausibility rule with the envelope's year 9999 as the upper bound). A topic that is
  both an availability topic and a point topic, and a `topics` override key that no point uses, are refused by the
  factory (R13, R15). The subscription set moved out of the directory the supervisor prunes (Q7 amended, R14);
  a removed input's persistent session still queues on the broker until it expires or is cleared, which the docs
  state with the remedy. Messages are acknowledged manually, after the router handled them (R15): a QoS 1 message
  received by a connect that `Close` abandons is no longer acknowledged, so the broker delivers it again to the
  next connection and the abandoned-connect window is closed.
- **Not done, deferred (known limits):** a JSON `null` is accepted for `persistent_session` and the `tls`
  strings, and `mqtt://b:` with an empty port is rewritten to the default (Task 1); the decoder takes hex floats and
  a leading `+` in plain text and does not check `float32` precision (Task 2); an availability test with two
  trailing calls that assert nothing (Task 3); a refused SUBACK retried forever with only a debug log,
  `connected` true before the SUBACK, and a test hook in the production struct (Task 5);
  `probe` discards the decoder's error kinds, dropped leaves are not marked in `browse`, client ids are asserted
  indirectly, and the `cmd` tests use real waits of 1 to 1.5 seconds (Task 6); the minors of
  `.superpowers/sdd/2026-11-06-mqtt-json/task-*-review.md`. Compatibility with other brokers (Mosquitto, EMQX, a
  gateway's built-in broker) and TLS client certificates against a real broker are not tested in CI: declared
  limit.
- **Follow-up (2026-11-17), branch `fix/mqtt-known-limits`:** closed the known limits above. A JSON `null` for
  `persistent_session` and every string field of the connection, the `tls` ones included, is refused with the
  field's type error, and `mqtt://b:` is refused as `connection.broker: empty port`. Plain text numbers follow the
  JSON number grammar with one leading `+` (hex floats, `inf`, `nan`, underscores and leading zeros are
  `conversion`), and a `float32` underflow is `conversion`. The availability test's two calls that asserted
