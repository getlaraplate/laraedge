# MQTT driver, JSON and plain payloads. Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax. Tick each step when it is done, in the same work block.

**Goal:** a read-only `mqtt` input that subscribes to a broker over MQTT 3.1.1 (TCP or TLS, optional authentication), turns JSON and plain payloads into typed samples through `topic|path` addresses, keeps its devices alive while the broker is connected, kills and revives them through optional availability topics, and offers `probe` and `browse`, tested against a broker started inside the tests.

**Architecture:** the driver `internal/input/mqtt`: connection and address parsing, a pure message decoder (payload to samples), an availability tracker on top of the core's `input.Lifecycle`, a small client interface with an adapter over paho, and the input itself (one goroutine owning the connection, its own reconnect loop with the driver kit's backoff, the subscription set persisted per input). It registers in the `run` driver registry, becomes accepted by `CheckBuild`, and plugs into `probe` and `browse`.

**Tech Stack:** Go 1.27; new dependency `github.com/eclipse/paho.mqtt.golang` v1.5.1 (`EPL-2.0 or BSD-3-Clause`, taken under BSD-3-Clause; brings `github.com/gorilla/websocket`, `golang.org/x/net`, `golang.org/x/sync`); test-only dependency `github.com/mochi-mqtt/server/v2` v2.7.9 (MIT). Both approved by the user before Task 4 starts.

**Spec:** `../specs/2026-11-06-mqtt-driver-design.md` sections 2 to 6 and 8 (plan 1); parent `../../../../docs/superpowers/specs/2026-10-12-laraplate-edge-agent-design.md` 9.1, 9.2; `../specs/2026-10-19-transforms-modbus-opcua-design.md` D6 and section 7 (driver kit, `probe`).

## Global Constraints

- AGPL-3.0 repo; permissive dependencies only; no CGO; module `github.com/getlaraplate/laraedge`; work on a feature branch from `develop`, merged through a pull request into `develop`.
- `gofmt -l .` empty, `go vet ./...`, `go test -race ./...`, `GOARCH=386 go test ./...`, `GOOS=windows go vet ./...` before every commit; table-driven tests; fakes over mocks; fake clock for scheduling, no sleeps or timing assertions (`clock.Fake.BlockUntil` to wait for timers).
- The driver never publishes: no `Publish` call anywhere in `internal/input/mqtt` in this plan (Sparkplug rebirth is plan 2).
- Input contract (core R47, spec D6): `Start` reads only local files (TLS) and returns; the broker connection runs in the background; an unreachable broker is death after `death_tolerance`, never a failing `Start`.
- Payload values, passwords and connection settings never appear in errors or logs at info and above; paho's package loggers stay at their silent defaults.
- Spec values exactly: `broker` schemes `mqtt` (port 1883) and `mqtts` (port 8883); `client_id` default `laraplate-edge-<agent_id>-<input_id>`; `qos` 0 or 1, default 1; `persistent_session` default `true`; `keepalive` default `30s`; `max_payload` default 256 KiB; `format` `json` (default) and `sparkplug_b`; timestamp formats `rfc3339`, `unix_s`, `unix_ms`; address `<topic>[|<path>]`, split at the first `|`; `+` and `#` refused in a point topic; plain `bool` accepts `true`/`false`, `1`/`0`, `on`/`off`, case-insensitive; command client ids `<client_id>-probe` and `<client_id>-browse`, clean session, QoS 0; read error kinds `payload_too_large`, `malformed_json`, `bad_timestamp`, `conversion`, `availability`, `unmapped`, plus the kit's `connection`.
- Commit only your own files in laraedge; never push; no `Co-Authored-By` trailer; do not commit at the stack root.

## Decisions taken in this plan

- **Q1. Driver configuration is validated by the factory**, as modbus M1: the schema keeps `connection` open (core R6), so the spec's "JSON Schema of the connection" is this factory validation, shown offline by `config validate` through the registry. Fixed messages naming the field path, never a value.
- **Q2. Devices are alive while the broker is connected.** `input.Lifecycle` kills a device after `death_tolerance` without `Read`. While connected, the input calls `Read` for every device that is not held dead by its availability topic, on connection and then every `death_tolerance / 2`. So silence never kills, a broker outage beyond the tolerance kills every device, and the reconnection gives the birth at once (the spec, which said "at its first sample after the connection", was amended with this plan).
- **Q3. Death on demand.** `input.Lifecycle` gains `Die(device string)`: emits death now for a live, known device, no-op otherwise. The `offline` availability payload calls it; `online` or a sample of that device calls `Read`.
- **Q4. Integers stay exact.** JSON is decoded with `json.Decoder.UseNumber`; a number goes to an integer type only when it parses as an integer in the type's range (`3.0` and `1e3` are not integers: `bad`); `uint64` above 2^63-1 is `bad` (model integers are int64, as modbus); `float32`/`float64` take the float value, non-finite is `bad`.
- **Q5. `max_payload`** is an integer number of bytes or a string with suffix `KiB` or `MiB` (`"256KiB"`), from 1 byte to 16 MiB; the check happens before any parsing.
- **Q6. Read error kinds** of this driver are exposed from their first count (the status endpoint already adds kinds outside `input.ReadErrorKinds`); `input.ReadErrorKinds` is not extended, so other drivers do not gain mqtt series.
- **Q7. The subscription set** of an input is `data_dir/inputs/{input_id}/mqtt-topics.json` (a sorted JSON list of topics), written with `atomicfile.Write` after the subscriptions of a connection are acknowledged. At connection the input unsubscribes the topics of that file it no longer uses, then subscribes its own. The directory is the one transform state already uses.
- **Q8. `format: sparkplug_b`** and `rebirth` are refused by this build with `connection.format: not available in this build` (plan 2).
- **Q9. `probe` waits** for the first sample of every point until all points have one or the command's 30 s timeout ends; points without a message are printed as `no message`. `Probe` returns the samples it has when ctx ends, without an error.
- **Q10. Test broker.** mochi in process, plain TCP and a TLS listener with a certificate generated by the test, the auth hook for user and password; one helper in `internal/input/mqtt/mqtttest` (test files and a test-only package).

## Review Focus

- The agent is stopped while a device publishes with QoS 1; after restart with the same persistent session the messages published meanwhile arrive as samples, in order. Test in Task 5.
- A JSON integer field that overflows the point type (`70000` into `int16`), a float into an integer type (`3.5`, `3.0`), `1e400`, and a 20-digit integer: each is a `bad` sample with kind `conversion`, never a panic or a rounded value. Test in Task 2.
- A retained `offline` Last Will on the availability topic when the input starts: the device gets death right after the supervisor's birth, and no keep-alive `Read` revives it until `online` or a sample arrives. Test in Task 5.
- A reload that removes a topic: the topic is unsubscribed at the next connection; a message of it still queued in the session is dropped with kind `unmapped`, never emitted. Test in Task 5.
- `probe` and `browse` run while the agent's input is connected: the agent stays connected (different client ids). Test in Task 6.
